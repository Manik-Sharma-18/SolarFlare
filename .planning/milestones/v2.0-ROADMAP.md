# Milestone v2.0: Stabilization & Cross-Platform

**Status:** SHIPPED 2026-02-04
**Phases:** 1-6
**Total Plans:** 16

## Overview

This roadmap took SolarFlare from a CUDA-only research prototype to a hardened, cross-platform training pipeline. The journey started by cleaning tech debt and establishing device detection, then layered on error handling, checkpoint resilience, data pipeline improvements, and MPS-specific optimizations. Test coverage validated each layer as the final gate before declaring stabilization complete.

## Milestone Summary

**Key Decisions:**
- Four public functions replace single get_device(); device resolved once at startup
- MPS always gets DummyGradScaler; real GradScaler only for CUDA
- Top-level `device: auto` replaces nested `device.use_cuda` boolean
- ConfigValidationError accumulates all errors, raises once
- NaN check before backward pass prevents wasted computation
- Emergency checkpoints use EMERGENCY_ prefix and metadata flag
- load_checkpoint always maps to CPU; caller handles device placement
- Augmentation deterministic via index multiplication, not random per-sample
- mmap handles opened lazily (safe for spawn/fork)
- Whole-file split via seeded random.Random shuffle
- macOS uses spawn multiprocessing context; Linux uses default fork
- Welford's online algorithm for O(1) MC Dropout memory
- Gaussian approximation replaces torch.quantile for MPS safety
- gc.collect() before device cache clear for memory leak prevention
- Real synthetic .npy files for testing (no mocks)

**Issues Resolved:**
- Legacy ConvLSTM.py (698 lines) removed — organized modules are authoritative
- Hardcoded 'cuda' strings replaced with device API throughout codebase
- Silent data loading failures now caught with threshold-based abort
- NaN losses no longer corrupt training — detected and handled gracefully
- Training crashes no longer lose all progress — emergency checkpoints saved
- Memory-mapped loading prevents OOM on 10-50GB datasets
- MC Dropout uncertainty no longer OOMs — O(1) memory via Welford's algorithm

**Issues Deferred:**
- MPS runtime validation requires manual testing (no MPS CI)
- Cross-device resume (CUDA→MPS) requires manual hardware test
- Atomic write crash resilience requires kill-during-save manual test
- Long-run memory stability (50+ epochs) requires manual profiling

**Technical Debt Incurred:**
- safe_quantile() defined but unused (reserved for future quantification)
- Predictor forward() double-preprocess quirk when downsample_input=False (tests work around it)
- No automated MPS integration tests in CI (hardware-dependent)
