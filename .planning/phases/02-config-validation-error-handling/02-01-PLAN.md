  <name>Task 1: Create config validation module and wire into main.py</name>
  <files>utils/config_validator.py, utils/__init__.py, main.py, config.yaml</files>
  <action>
Create `utils/config_validator.py` with a single public function `validate_config(config: dict) -> None` that:

1. **Collects ALL errors before raising** — accumulate errors in a list, raise a single `ConfigValidationError` (custom exception, defined in same file) at the end listing every problem. This lets users fix everything in one pass.

2. **Required keys and type checks:**
   - `device` must be a string, one of "auto", "cuda", "mps", "cpu"
   - `seed` must be an int >= 0
   - `data.data_dir` or `data.preprocessed_dir` must be a string
   - `data.t_in` and `data.t_out` must be positive ints
   - `data.train_split` and `data.val_split` must be floats in (0, 1), and their sum must be < 1.0
   - `model.input_channels` must be a positive int
   - `model.channels` must be a list of positive ints with length >= 1
   - `model.kernel_size` must be a positive odd int
   - `training.batch_size` must be a positive int
   - `training.epochs` must be a positive int
   - `training.lr` must be a positive float
   - `training.patience` must be a positive int
   - `training.grad_clip` must be a positive float
   - `training.use_amp` must be a bool
   - `training.scheduler.type` must be one of "cosine", "step", "constant", "none"
   - `loss.type` must be one of "l1", "composite", "weighted"
   - `normalization.method` must be one of "asinh", "robust", "fixed"

3. **Cross-field validation (errors):**
   - `dual_channel: true` requires `input_channels >= 2` — error: "dual_channel is enabled but input_channels is {N} (must be >= 2)"
   - `use_amp: true` with `device: cpu` — error: "AMP enabled but device is 'cpu'; AMP requires CUDA or MPS"

4. **Warnings (print, do not abort):**
   - `lr > 0.01` — warning: "Learning rate {lr} is unusually high"
   - `batch_size > 16` — warning: "Batch size {bs} is high for spatiotemporal models; may cause OOM"
   - `patience > epochs` — warning: "patience ({p}) exceeds epochs ({e}); early stopping will never trigger"
   - `dropout_rate > 0` but `uncertainty.enabled: false` — warning: "Dropout enabled but uncertainty estimation disabled"

5. **Add new config fields to config.yaml** under a new `error_handling` section:
   ```yaml
   error_handling:
     max_consecutive_nan: 10       # Abort training after N consecutive NaN batches
     grad_norm_warning_threshold: 100.0  # Log warning when gradient norm exceeds this
     data_failure_threshold: 0.1   # Abort if more than this fraction of data files fail (0.1 = 10%)
   ```

6. **Wire into main.py:** Call `validate_config(config)` in `run_training()` immediately after `load_config()` returns and BEFORE `seed_everything()`. Import from utils. Also add to `utils/__init__.py` exports.

Use `logging` module for warnings (import logging, get logger). For errors, accumulate strings and raise at end.

Do NOT use `validate_config` to check data files — that happens in the loader (Task 2). Config validation is purely about the YAML structure and values.

Handle missing optional sections gracefully (e.g., if `uncertainty` section is absent, skip uncertainty-related warnings). Use `.get()` with defaults for optional fields.

<task type="auto">
  <name>Task 2: Add data file pre-flight scan with failure threshold</name>
  <files>solarflare_data/loader.py</files>
  <action>
Modify `load_and_prepare_data()` in `solarflare_data/loader.py` to add a pre-flight validation scan BEFORE the existing loading loop:

1. **Pre-flight scan phase** (new code, inserted before the "First pass: collect statistics" loop):
   - Iterate through all discovered `.npy` files
   - For each file, attempt `np.load(file_path, mmap_mode='r')` (memory-mapped, minimal I/O) to verify the file is readable
   - Check that the loaded array is a structured array with required fields ('X', 'Y', 'time', 'windTotal') — use `data.dtype.names`
   - On failure, record `{filename: error_message}` in a `failed_files` dict
   - On success, record in a `valid_files` list

2. **Failure threshold check** (after scan):
   - Read threshold from caller or default to 0.1 (10%): Add `failure_threshold: float = 0.1` parameter to `load_and_prepare_data()`
   - If `len(failed_files) / len(npy_files) > failure_threshold`:
     - Print detailed failure report: each file and its error
     - Print summary: "{N} of {M} files failed validation ({pct}%), exceeding {threshold}% threshold"
     - Raise `DataValidationError` (define in same file) with same message
   - If some files failed but under threshold:
     - Print warning with each failed file and reason
     - Continue with only valid files
   - If zero files valid: raise as before

3. **Update the existing loading loop** to iterate over `valid_files` instead of `npy_files`. The existing try/except in the loading loop can remain as a secondary safety net (runtime load failures distinct from pre-flight validation).

4. **Also apply to `load_preprocessed_data()`**: Add similar pre-flight for `.npz` files — verify each is loadable and contains a 'data' key. Same threshold logic.

5. **Wire failure_threshold from config**: In `main.py`, pass `config.get('error_handling', {}).get('data_failure_threshold', 0.1)` as `failure_threshold` to both `load_and_prepare_data()` and `load_preprocessed_data()`.

Print a clear "Pre-flight data scan: {N}/{M} files OK" message after the scan completes.
